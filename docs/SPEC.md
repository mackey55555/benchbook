## 1. 概要・前提

**目的**：社会人リーグの公式戦で、マネージャーがベンチ側の控えスコアをiPhoneで記録する。オフィシャル席の公式記録と照合し、監督へファウル数・TO残数を即時に伝えられる状態をつくる。

**利用者**：自チームのマネージャー（1台で入力）。閲覧はPDF/画像で共有。

**スコープ（MVP）**

- 両チームの得点・ファウルを背番号付きで記録（必須）
- リバウンド（OR/DR）・アシスト・スティール・ブロック・ターンオーバー（任意入力、両チーム同一UI）
- チームファウル・TO残数・退場/失格の自動判定と警告
- Q終了時の照合フロー、延長対応
- 出力：公式様式のランニングスコア（画面＋PDF）、詳細画面（ボックススコア・プレー一覧・Q別得点）
- 試合データのJSONエクスポート/インポート
- 選手交代の記録（任意）。コート上の5人の表示、出場時間、+/-。交代時に会場の時計の残り時間を任意で入力する（2026-11-16 追加）
- 手元の時計（任意）。動かす・止める・合わせるができ、動かしたQの記録には残り時間が自動で付く（2026-11-17 追加。マネージャーの要望）
- チームの記録（選手につかないTOV・リバウンド）、あとで見直すための印、試合中のランニングスコア表示（2026-11-17 追加。同上）
- 時間を使う集計（2026-11-17 追加）：試合ごとの「試合の流れ」シート（得点の流れのグラフ、時間帯別の得点、連続得点・無得点、コート上の組み合わせ）、プレー一覧のPDF、分析の「時間帯別の平均得点」「5人の組み合わせ」「40分換算」

**非スコープ（やらない）**

- 公式スコアシートの代替（オフィシャル業務での使用は想定しない）
- 公式の計時・ショットクロック管理（時計は手元の目安で、公式の時間は会場の時計にしたがう）
- サーバー同期・Web閲覧・複数端末同時入力
- App Store公開

## 2. 技術構成と配布

| 領域 | 採用 | 理由 |
|---|---|---|
| アプリ | Expo（最新SDK）+ expo-router + TypeScript | iPhoneネイティブ、OTA可 |
| ローカルDB | expo-sqlite + Drizzle ORM（マイグレーション管理） | 端末内で完結、Safariのストレージ削除リスクなし |
| 端末機能 | expo-haptics / expo-keep-awake / expo-screen-orientation | 押下フィードバック・画面消灯防止・横向き固定 |
| 出力 | HTML生成 → 画面はWebView表示、PDFはexpo-print、共有はexpo-sharing | ランニングスコア描画を1実装で画面とPDFに共用 |
| ビルド | EAS Build `preview` プロファイル（iOS ad hoc 内部配布） | ストア審査なし。端末UDIDの事前登録が必要 |
| 更新 | EAS Update（channel: `preview`、runtimeVersion: fingerprint） | JS変更は審査なしで配信。無料枠で収まる |
| サーバー | なし | ランニングコスト0円 |

**運用上の制約**

- 新しい端末を追加するたびに `eas device:create` → 再ビルド → 再インストールが必要
- ad hoc配布は配布証明書の有効期限（1年）に依存 → 年1回の再ビルドが必要
- ネイティブモジュール追加・SDK更新はOTA不可 → 再ビルド・再インストール
- 将来、他チーム配布する場合はUDID上限（年100台）があるためストア公開へ切り替える

## 3. ルール定義（JBA＝FIBA準拠、設定で調整可）

ルールは純粋関数のルールエンジン（`src/domain/rules.ts`）に集約し、UIから直接判定しない。

| 項目 | 既定値 | 設定可 |
|---|---|---|
| Q数・時間 | 4Q × 10分 | Q時間（リーグ独自ルール対応） |
| 延長 | 5分、決着まで繰り返し | 延長時間 |
| 登録選手数 | 1チーム最大12名 | 上限値 |
| TO | 前半2回 / 後半3回 / 延長は各1回、未使用分は繰り越さない | — |
| 第4Q残り2分の制限 | 残り2分以降はTO最大2回 | 手動トグル「残り2分」で適用（クロック非管理のため） |
| チームファウル | Qごとに集計。5つ目以降はペナルティ（FT）表示。延長は第4Qの累計を継続 | — |
| チームファウルに数えるもの | 選手のP/T/U/D | HC・ベンチのファウル（C/B）は数えない |

**選手の退場・失格判定**

- ファウル合計（P+T+U+D）が5 → 退場
- T×2、U×2、またはT×1＋U×1 → 失格
- D → 即失格
- 4ファウル時点で警告表示

**HCの失格判定**

- C×2 → 失格
- C・Bの合計が3 → 失格

**ファウル記録の属性**：種類（P/T/U/D/C/B）＋与えたFT数（0〜3）。スコアシート表記（例：P2、U2）はこの2属性から生成する。

## 4. データモデル（SQLite）

**原則：イベントソーシング。** 得点・ファウル数などの集計値は保存せず、`game_events` から都度導出する。取消は物理削除せず `voided_at` で論理削除。修正は「元イベントをvoid＋同じ `order_key` で新イベント挿入」とし、履歴を残す。

| テーブル | 主なカラム |
|---|---|
| `teams` | id, name, is_own, created_at |
| `players` | id, team_id, number, name, is_active |
| `games` | id, date, league_name, venue, own_side（A/B）, team_a_name, team_b_name, period_minutes, ot_minutes, status（prep / live / finished）, current_period, created_at, finished_at |
| `game_roster` | id, game_id, side（A/B）, player_id（相手チームはnull可）, number, name, is_starter, is_captain |
| `game_staff` | id, game_id, side, role（HC/AC）, name |
| `game_events` | id（ULID）, game_id, order_key（REAL）, period（1〜4、5以降は延長）, side, roster_id（null=チーム/ベンチ）, type, foul_kind, ft_awarded, clock_seconds, created_at, voided_at, replaces_event_id |
| `period_checks` | game_id, period, score_a, score_b, team_fouls_a, team_fouls_b, matched（bool）, note, confirmed_at |

※ `game_roster` には背番号と氏名をスナップショットで保持し、後から選手マスタを変えても過去の試合記録が変わらないようにする。

**イベント種別（type）**

| type | 意味 | 得点 |
|---|---|---|
| `FG2_MADE` / `FG2_MISS` | 2P成功 / 失敗 | 2 / 0 |
| `FG3_MADE` / `FG3_MISS` | 3P成功 / 失敗 | 3 / 0 |
| `FT_MADE` / `FT_MISS` | FT成功 / 失敗 | 1 / 0 |
| `OREB` / `DREB` | オフェンス / ディフェンスリバウンド | — |
| `AST` / `STL` / `BLK` / `TOV` | アシスト / スティール / ブロック / ターンオーバー | — |
| `FOUL` | foul_kind（P/T/U/D/C/B）＋ ft_awarded | — |
| `TIMEOUT` | side単位（roster_idはnull） | — |
| `PERIOD_END` | Q終了の区切り | — |
| `L2M` | 第4Q「残り2分」トグルをONにした位置のマーカー（OFFでvoid）。TO上限の計算に使う | — |
| `SUB_IN` / `SUB_OUT` | 選手交代。`clock_seconds`（そのピリオドの残り秒、任意）を持つ。1回の交代は同じ `created_at` で記録する | — |

※ `PERIOD_END` と `L2M` はチームに属さないため `side` は null。

**交代と出場時間**（`src/domain/lineup.ts`）

- コート上の選手＝先発（`game_roster.is_starter`）から始めて `SUB_IN` / `SUB_OUT` を記録順に適用したもの
- 先発が選ばれている、または交代の記録があるチームだけを「交代を管理している」とみなす（相手チームは任意）
- 出場時間：残り時間付きの交代はその時刻、時刻なしの交代は直前に分かっている時刻（ピリオド開始・終了、前の時刻付き交代）で計算する。プレー中の時刻なし交代を含む選手は概算として「約」を付ける
- +/-：出場中のチーム得失点差

**ドメイン関数（純粋関数・単体テスト必須）**：`computeScore` / `computeTeamFouls(period)` / `computePlayerFouls` / `checkDisqualification` / `remainingTimeouts` / `buildRunningScore` / `buildBoxScore`

## 5. 画面仕様

### 5-1. ホームと下メニュー

縦画面の4タブ（ホーム・試合・分析・設定）を下メニューで切り替える。試合準備・入力・照合・試合詳細・チーム管理・バックアップは下メニューなしで開く（入力中の誤タップを防ぐ）。

- ホーム：新規試合、直近5試合（日付・対戦相手・スコア・状態）。進行中（status=live）の試合があれば最上部に「再開」を大きく表示
- 試合：全試合の一覧。20件ずつ表示し、最下部の「さらに読み込む」で増やす。期間（すべて・今月・3か月・今年度〈4月始まり〉）、勝敗（勝ち・負け・引分）、チーム名・大会名・会場の部分一致で絞り込める。勝敗で絞ると終了した試合だけが残る。長押しで削除
- 分析：終了した試合を自チーム（own_side）の視点で集計する。「チーム」と「選手」の2軸を切り替え、どちらも期間で絞り込み、1試合平均と合計を切り替えられる
  - 項目は、得点、2P・3P・FTの成功数／試投数／成功率、OF・DF・合計リバウンド、アシスト、スティール、ブロック、ターンオーバー、ファウル。成功率は平均にせず、期間全体の成功数÷試投数で出す
  - 項目の並び順と見出しは、試合ごとのボックススコアのシートに合わせる（PTS、3P、2P、FT、F、OR・DR・TR、TO、AS、ST、BS、MIN、+/-）。共有用のシートの表は、ボックススコアと同じ書式（枠つきの見出し、2段の項目名、黒の罫線）にする
  - 選手には、出場時間（MIN）と +/-（出場中の得失点差）も出す。先発と交代を記録した試合の分だけを集計し、平均もその試合数で割る。記録のない選手・試合は「-」
  - チーム：戦績、平均得点・失点、得失点差／試合ごとの推移（直近10試合、項目を選べる、自チームと相手の棒グラフ。棒をタップするとその試合の値を出し、試合詳細を開ける）／Q別の平均得点（第1〜4Q）／シュート成功率／全項目の自チームと相手の比較
  - 選手：全選手・全項目の比較表。見出しをタップするとその項目の多い順に並べ替える。選手をタップすると詳細ページを開く
  - 選手の詳細ページ：背番号・氏名・試合数、得点・リバウンド・アシストの平均と合計、全項目（平均／合計）、シュート成功率、試合ごとの推移（項目を選べる）、試合ごとの成績（新しい順。タップで試合詳細）
  - 選手は選手マスタで同一人物とみなし、マスタに無い選手は背番号と氏名で束ねる。試合数は出場登録された試合の数
  - 共有：チーム成績・選手の比較表・選手の詳細ページのそれぞれに「共有」を置く。いま見ている期間・平均／合計・並び順でA4のシートを作り、PDFまたは画像（内容全体を1枚）で共有シートに渡す
  - 分析タブの「共有」からは、選んでいる期間の全内容（チーム成績、選手の比較表、記録のある選手1人ずつのまとめ）を1つのPDFにまとめて出力することもできる。シートごとに改ページする
- 設定：使い方、チーム・選手の管理、バックアップ、アプリ情報と更新の手動確認
- はじめての人向けの案内
  - 練習用の試合：架空の2チーム（5人ずつ）で、入力画面の上部に「練習 2/10　『2P○』をタップ」のように次に押す場所を1つずつ示し、その場所をオレンジの枠で囲む
    - 手順：①自チームの選手を選ぶ → ②2P○ → ③選手を選ぶ → ④FOUL → ⑤取り消す → ⑥選手を選ぶ → ⑦FOULを長押しして種類を選ぶ → ⑧タイムアウト → ⑨ファウル状況を見る → ⑩Q終了 → 照合で「一致」。「一致」で練習は終わり、ホームに戻る
    - 案内の右の「スキップ」（またはメニュー）で、「練習をスキップしますか？『設定 → 使い方』から、いつでもやり直せます」と確認してから終わる
  - 練習用の試合は1つだけ（固定のID）で、一覧・分析・再開・バックアップの対象にしない。終わったとき、スキップしたとき、ホームに戻ったときに消す。選手マスタや実際の試合には触れない
  - 入口：はじめて開いたとき（試合がまだ無いとき）に一度だけ「はじめに、練習してみますか？」と尋ねる（スキップ可。尋ねたことは端末内の印で覚える）。ほかに、試合が1つもないときのホームの「はじめての方へ」と、設定の「使い方」。進行中の試合があるときは「使い方」からは始められない
  - 使い方ページ：項目をタップすると説明が開く。項目は、試合を始める／試合中の入力／ファウルとタイムアウト（種類の選び方を含む）／選手の交代／Qの終わりと第4Q・延長（残り2分を含む）／試合のあと（スコアシートと共有）／成績を見る（分析）／成績を共有する／記録を守る
  - 各画面の「？」：試合準備・試合詳細・分析・バックアップの右上に置き、使い方ページのその項目を開いた状態で表示する。横向きの画面（入力・照合）には置かない

### 5-2. チーム管理

- 自チームの選手マスタ（背番号・氏名・有効/無効）
- 相手チームも保存できる（リーグ戦での再戦時に呼び出す）

### 5-3. 試合準備

- 日付・大会名・会場、相手チーム（保存済みから選択または新規入力）
- 自チームがスコアシート上のA/Bどちらか
- Q時間・延長時間（既定は10分/5分）
- 出場登録（最大12名）、スターター5名、キャプテン、HC名
- 保存済みチームを読み込むときに、今日来ている選手を選べる（任意。選手マスタが12名を超えるチームのため）
- 相手チームは背番号のみでも開始可。氏名は任意

### 5-4. 試合中入力（横画面固定・1画面完結）

```
┌────────────┬─────────────────┬────────────┐
│ A チーム   │  52 - 48   Q3   │ B チーム   │
│ TF:3 TO:1  │   [Q終了]       │ TF:4 TO:2  │
├────────────┤ [2P○][3P○][FT○] ├────────────┤
│ 4  5  6    │ [2P×][3P×][FT×] │ 4  5  6    │
│ 7  8  9    │ [OR ][DR ][AST] │ 7  8  9    │
│10 11 12    │ [STL][BLK][TOV] │10 11 12    │
│13 14 [ベンチ]│ [  FOUL  ]      │13 14 [ベンチ]│
├────────────┴─────────────────┴────────────┤
│ [↶ UNDO]  直近: #7 3P○ / B#10 DR / ...      │
└─────────────────────────────────────────────┘
```

**操作フロー**

- 選手ボタン → アクションボタンの2タップで1イベント確定。確定時に触覚フィードバック（成功系は軽く、ファウルは強め）
- 確定後、選手選択は必ず解除する（次のプレーを別選手に誤って紐づけないため）。FTも例外にせず、1本ごとに選手をタップし直す
- FOUL：タップでP（FT数0）を即記録。長押しで種類（P/T/U/D）とFT数（0〜3）を選ぶシート
- [チーム]ボタン（旧[ベンチ]）またはヘッダーのチーム名 → TOV / OR / DR：チームの記録（24秒オーバーなどのチームのTOV、選手につかないチームリバウンド）。`roster_id` が null のイベントとして保存し、ボックススコアでは「チーム」の行と合計に入る
- [チーム]ボタン → FOUL：HC/ベンチのファウル（C/B）
- TO：ヘッダーのTO表示をタップ → 確認後に記録。残り0回のときは押せない
- [Q終了]：確認ダイアログ → 5-5へ
- UNDO：直前の有効イベントをvoid。直近ログのタップで全ログシートを開き、選手・種類の修正と削除ができる

**時計・印・ランニングスコア・誤タップ防止（2026-11-17 追加）**

- 時計：ヘッダー中央。タップで動かす・止める、長押し（またはメニュー）で残り時間を合わせる。状態は `games.clock_period / clock_remaining_ms / clock_started_at` に持ち、動いている間は端末の時刻との差で残りを出す（アプリを閉じても進む）。残り0で自動で止まり、Q終了でも止まる。次のQはピリオドの長さから始まる
- 時計を動かした（または合わせた）Qでは、得点・ファウル・TO・交代・印に残り時間（`clock_seconds`）を自動で付ける。一度も使わないQの記録には付けない。交代シートの残り時間には自動で入り、打ち直せる
- 印：[印]で `MARK` イベントをその位置に入れる。集計には影響しない。直前が印のときにもう一度押すと外れる。UNDOは印を飛ばす。ログでは目立つ行で表示し、件数を[ログ]ボタンに出す
- ランニングスコア：ヘッダーの[スコア]で、現在までのランニングスコア（6章の様式）をいつでも開ける
- 交代を記録しているチームでは、コートに出ていない選手はタップしても選ばれない（理由を1行で知らせる）。出ていない選手への記録（失格など）は長押しで選ぶ

**表示ルール**

- ボタンは最小56pt角。各チーム最大12名＋ベンチを3列グリッドで表示
- 4ファウルの選手は赤で表示。退場・失格の選手はグレーアウトして押せない
- チームファウルが4に達したら「次からFT」バッジを表示
- 第4Qのみ「残り2分」トグルを表示（ONでTO上限を適用）

### 5-4b. 時間を使う集計（2026-11-17 追加）

集計は `src/domain/timeline.ts`、帳票は `src/output/gameFlowHtml.ts` に置く。

- **時刻の決め方**：時刻は「試合開始からの経過秒」で持つ。ピリオドごとに、プレーの記録（交代と印を除く）の7割以上に残り時間が付いていれば「時計を使ったピリオド」とみなし、その残り時間を使う（付いていない記録は直前の時刻を引き継ぐ。時計を直して時刻が前後しても、並びは記録順を守る）。それ以外のピリオドは、記録を等間隔に並べる（順番は正しいが、時刻は目安）
- **得点の流れ**：全試合で出す。時計を使っていないピリオドは「＊」を付け、等間隔であることを注記する
- **時間帯別**：各ピリオドを前半・後半に分け、第4Qは残り2分を内数で出す。時計を使ったピリオドだけ。分析（期間の平均）には、規定の4ピリオドすべてで時計を使った試合だけを入れ、対象の試合数を表示する。延長は平均に入れない
- **連続得点**：相手に得点を許さずに取った点の最大。全試合で出す
- **無得点の時間**：記録のあるピリオドすべてで時計を使った試合だけ
- **コート上の組み合わせ**：先発と交代を記録したチームだけ。時刻の扱いは出場時間（MIN）と同じ。分析では、選手マスタで同じ5人を試合をまたいで束ねる
- **40分換算**（選手の分析）：出場時間のある試合の成績 × 40分 ÷ 出場時間。出場時間が5分未満の選手は出さない。成功率はそのまま、出場時間は1試合平均を出す
- 時間はすべて手元の時計によるもので、帳票に「公式の時間ではない」と明記する

### 5-5. Q終了・照合

- そのQ終了時点の得点・チームファウル・TO残数を両チーム分、大きく表示
- [一致] → `period_checks` に記録して次のQへ
- [修正する] → 選手別の修正表を開く。修正後に再度照合
  - 両チームの選手ごとに、そのQの 2P・3P・FT の成功数とファウル数を表示する。マスを選び「−1」「＋1」で1件ずつ直す
  - ＋1 はそのQの最後の記録の直後に入る（ファウルは P・FT0）。−1 はその選手・Q・項目の最後の1件を取り消す（void）
  - 順番・ファウルの種類・その他の項目まで直すときは、修正表からログ（そのQに絞り込み）を開く
- 第4Q終了時に同点なら、延長に進むか、同点のまま試合終了にするかを選ぶ（引き分けのある大会・練習試合のため）。同点でなければ試合終了（status=finished）
- 照合画面から、現在までのランニングスコアを表示できる

### 5-6. 試合後・詳細

- タブ1：ランニングスコア（6章）
- タブ2：ボックススコア（両チーム、Q別フィルタ）。項目：PTS、2PM-A、3PM-A、FTM-A、OREB、DREB、REB、AST、STL、BLK、TOV、PF
- タブ3：プレー一覧（時系列、Qで絞り込み）
- タブ4：Q別得点
- 共有：PDF、画像、JSON
- 「得点・ファウルを直す」で、5-5 と同じ選手別の修正表をQを切り替えながら使える（試合後にビデオを見返して直す用途）。ログでの修正・削除もできる

## 6. ランニングスコア出力仕様

- `buildRunningScore(events)` が、チームごとに累計点（1〜160）と、その点を取った背番号・得点種別・Qの対応表を返す。描画はこの結果だけを使う
- 描画はHTMLで1実装とし、画面（WebView）とPDF（expo-print）で同じものを使う
- レイアウトは公式スコアシートのランニングスコア欄に合わせ、A/Bの2列を1組として4組（1〜40、41〜80、81〜120、121〜160）並べる
- 記号
  - 2P：累計点の数字に斜線を引き、横に背番号
  - 3P：同じく斜線＋背番号を丸で囲む
  - FT：黒丸＋背番号
  - Q終了：最後の得点を丸で囲み、その下に横線
- Qごとの色分けは設定値にする（正しい記入要領は未決事項で確認）
- ヘッダーと付帯欄：大会名・日付・会場・チーム名、選手ごとのファウル欄（種類とFT数、Qごとの色）、TO欄（時刻は空欄）、Q別得点、最終スコア
- PDFはA4縦。スコアシートのレイアウトに近づけるが、公式様式の完全な再現は目指さない

## 7. 非機能要件

**信頼性（最優先）**

- 通信は一切しなくても全機能が動く
- 各イベントはSQLiteへの書き込み（トランザクション）が完了してからUIに反映する。アプリが強制終了しても、確定済みのイベントは失われない
- 起動時に進行中の試合があれば、その試合の入力画面へ直接戻る
- 試合中は画面を消灯させず（keep-awake）、横向きに固定する

**OTA制御**

- `checkAutomatically: NEVER` にし、自動では更新を確認しない
- 進行中の試合がないときだけ、ホーム画面で更新を確認・取得する（ホームを開いたとき・アプリに戻ったときに自動で確認。間隔は5分以上）
- 取得できたらホーム上部に「最新版があります／更新する」を出し、押すとその場で再読み込みして適用する。押さなければ次回の起動時に適用される
- runtimeVersionはfingerprint方式（ネイティブ構成が変わったビルドには古いOTAを配信しない）

**データ保全**

- DBマイグレーションは前方互換のみ（Drizzle）。既存データのフィクスチャで移行テストを行う
- JSONで、試合単位と全データの両方を書き出し・読み込みできる（共有シート経由）
- 試合終了時に「バックアップを書き出す」を促す

**性能**：タップから触覚フィードバックまで100ms以内を目標にする

**ここは構想で、未実装。** 1〜9章の仕様（1台で完結・サーバーなし）を変えるものではなく、実装を決めた時点で各章に反映する。

### 10-1. 想定する利用者

- 主な対象は社会人リーグのチーム。お金を出すのはチームの運営者で、記録はマネージャーや当番の記録係がつける
- 選手本人が自分の成績を見たがるので、「メンバー全員が自分のスマホで見られる」ことを有料の価値にする

### 10-2. 役割と状態

役割は「運営者」と「メンバー」の2つだけにする。マネージャー・記録係・選手はすべてメンバーで、記録も閲覧も共有もできる（運営者やキャプテンしか共有できないのは不便なため）。

ログインなしで見られる閲覧ページは作らない（氏名と成績が出るため）。チームの内容を見られるのはメンバーだけ。アプリを入れられない人（Android版が出るまでのAndroidの人など）には、メンバーがPDF・画像のファイルで共有する。

| 名前 | 説明 | アカウント |
|---|---|---|
| 未加入 | チームに入らず1台で使う。今のアプリと同じ | 不要 |
| 運営者 | チームを作り、支払いをし、メンバーを招待する | 必要 |
| メンバー | 運営者に招待された人（マネージャー、記録係、選手） | 必要 |
| 解約後 | 契約が切れたチームの運営者・メンバー | あり |

### 10-2b. 「個人」と「チーム」の切り替え（案）

アプリの中に、記録の置き場所を2種類持つ。運営者もメンバーも、画面上部で切り替えて使う。

| 置き場所 | 数 | 保存先 | 料金 | アカウント |
|---|---|---|---|---|
| 個人 | 1人に1つ | 端末内だけ | 無料（分析は直近3試合） | 不要 |
| チーム | 複数に入れる | サーバー（端末にも写しを持ち、電波がなくても記録できる） | チームごとに契約が必要 | 必要 |

- 10-2の「未加入」は、個人だけを使っている状態のこと。チームに入っても個人は残る
- 試合・名簿・分析は、置き場所ごとに別々。試合は作ったときの置き場所に属し、1つの試合が属するのは1か所だけ
- 個人の試合は「チームに送る」でチームへ写せる（10-5の流れ）。掛け持ちの人は、試合ごとに送り先のチームを選ぶ
- チームの契約が切れると、そのチームは開けなくなる。個人とほかのチームには影響しない
- 進行中の試合は、置き場所をまたいで同時に1つだけ
- 権利（分析の期間制限の解除など）は置き場所に付ける作りにする。そうしておけば、個人だけを有料にするプランをあとから足せる。ただし最初に出すのはチームプランだけ（10-4）
- 1人が運営者になれるチームは5まで（決定）。メンバーとして入るチームの数に制限はない。5を超える要望が出たら段階を足す（段階の追加は既存の契約に影響しない）
- 複数チーム分の支払いは、段階つきの商品で行う（決定）。アプリ内課金の定期購読は同じ商品を1つのApple IDで同時に複数契約できないため、「1チーム」〜「5チーム」の段階を1つのグループに用意し、段階を上げると契約できるチーム数（枠）が増える。最初の公開から入れる（あとから足すと、必要になった人がその時点で離れるため）
  - 月額と年額を用意し、年額は割り引く。チーム数による割引はしない（料金はチーム数に比例）。商品は10個（5段階×2）
  - 契約は運営者のアカウントに付き、運営者が自分のチームに枠を割り当てる。割り当ては、枠の数の範囲でいつでも入れ替えられる
  - 段階を上げたときは、差額がその場で精算され、すぐ枠が増える
  - 段階を下げるときは、アプリ内の「プランを変更」で、残すチームを先に選んでから手続きに進む。枠が減るのは次の更新日から
  - 端末の設定アプリから直接段階を下げた場合は、アプリ内の流れを通らない。この場合は、次にアプリを開いたときと更新日の前に、残すチームを選ぶよう運営者に知らせる。更新日までに選ばれなければ、割り当てた順の古いチームから残し、外れたチームは開けなくなる（データは消さない。あとで入れ替えられる）
  - 全部を解約した場合は、更新日にすべてのチームが開けなくなる（選ぶ必要はない）

### 10-4. 方針

- **記録は止めない**：未加入でも解約後でも、試合の記録・修正・試合ごとの共有・バックアップは無料のまま使える。データを人質にしない
- **無料と有料の線（決定）**：1試合で完結する価値（記録、スコアシート、その試合の共有）は無料。分析は直近3試合だけ無料で、その範囲のPDF・画像共有もできる。試合がたまるほど増える価値（シーズンの分析、選手ページ、まとめPDF）と、チームでの共有は有料
- **プランはチームプランの1つだけ（決定）**：入ると、分析の期間の制限がなくなり、メンバー全員がアプリで同じ内容を見られるので、ファイルを作って送る手間もなくなる。1人用の安いプランや買い切りは作らない
- **1つの試合を記録するのは1台**：試合は記録した端末からサーバーへ送る。複数の端末で同じ試合を同時に書き換える同期は作らない（要望が出てから検討）。送ったあとの修正は、ほかのメンバーもできる（修正の履歴は残る）
- **料金はチーム単位**：運営者が1契約すれば、メンバーの人数によらず同じ額。月額と年額を用意し、年額は割り引く（金額は未決）
- **広告（未決）**：無料版に入れるなら、試合中の画面（入力・照合）には絶対に出さない。候補はホームのバナーと、PDF・画像を共有するときの全画面広告。チームプランでは広告を消す。10-7を参照
- **支払いはアプリ内課金**：運営者の契約をサーバー側でチームに紐づけ、メンバーはチームに入った時点で有料機能を使える。外部決済が使えるかは規約の確認が必要

### 10-5. チームプランを始めるときの流れ（案）

アカウントは、チームを作るとき・招待を受けるときに初めて作る。未加入で使うあいだはアカウント不要のまま。

**運営者（チームを作る）**

1. 設定の「チームプラン」からサインインする（アカウント作成）
2. チームを作る。端末の自チームの名簿が、そのままチームの名簿になる
3. チームプランを購入する
4. 端末にある終了済みの試合の一覧が出る。送る試合を選んで「チームに送る」（最初は全部に印が付いている）
5. 招待リンクを発行してメンバーに送る

**メンバー（招待を受ける）**

1. 招待リンクを開き、アプリを入れてサインインする（アカウント作成）
2. チームに参加する。チームの名簿と試合が端末に届く
3. 端末に自分で記録した試合があれば、送る試合を選べる（最初は印なし。別チームの試合や、ほかの人がすでに送った試合が混ざりうるため）

**過去の試合の扱い**

- 自動で全部は送らない。選んで送る。あとから試合ごとに送ることもできる
- 同じ日・同じ相手の試合がすでにチームにあるときは、重複の可能性を知らせる
- メンバーの端末の選手は、チームの名簿と背番号・氏名で突き合わせる。合わない選手は、名簿のだれに当たるかを選ぶか、名簿に追加する

### 10-5b. サーバーの構成（案）

- **Supabase** を使う（データベース＝PostgreSQL、ログイン、アクセス制御）。リージョンは東京
  - 今の端末内のテーブル（SQLite＋Drizzle）とほぼ同じ形で持てる
  - 「自分が入っているチームの行だけ読める・書ける」をデータベース側の規則（RLS）で守る
  - ログインはAppleでサインインのほか、Android版に向けてGoogle・メールも使える
- **サーバーは保存と受け渡しだけ**：集計・分析・スコアシートの作成は、これまでどおり端末側で行う（`src/domain/` をそのまま使う）。サーバーに計算を持たせない
- **同期は自前で小さく作る**：Supabaseに「電波がなくても動く同期」は付いていない。端末のSQLiteを正とし、記録（追記型のイベント）をIDで重複なく送り、ほかの人の分は更新時刻の続きから取りに行く。1試合を書くのは1台（10-4）なので衝突の解決は名簿だけで済む
- **環境の持ち方**：開発は手元のパソコン上のSupabase（CLIとDocker）で行い、クラウドの枠は使わない。実際の人に試してもらう段階で、既存の有料の組織（IT-Streak と同じ組織）にBenchbook用のプロジェクトを追加する。基本料は組織に1回だけで、増えるのはプロジェクト分のサーバー代（金額は追加前に確認する）。ほかのサービスと同じプロジェクトには同居させない（ログインの利用者が混ざり、障害が及ぶため）
- **特別扱いのチーム**：チームに「契約なしで全機能を使える」印をサーバー側で付けられるようにする（自チームや協力チーム用）。印を付けるのは管理者がサーバーで直接行い、アプリ内に合言葉などを入力する画面は作らない（アプリ内で独自に機能を解放する仕組みはストアの規約で認められないため）。知り合いのチームへの割引は、Appleの公式の仕組み（定期購読のオファーコード：一定期間の無料・割引）で行う
- **サインイン（決定）**：Apple、Google、メールアドレスの3つを用意する
- **実装の場所**：`supabase/` にテーブル定義と権限の規則（migrations）、その自動テスト（tests）を置く。手元では `supabase start` で動かし、`supabase test db` でテストする。ポートは 5452x（ritocco の 5442x と重ならないようにしている）
- **テーブル**：利用者（profiles）、契約（subscriptions）、チーム（teams）、メンバー（team_members）、招待（team_invites）と、端末のテーブルと同じ形の内容（squads＝名簿のまとまり、squad_players、games、game_roster、game_staff、game_events、period_checks）。内容の各行はチームに属し、物理削除はせず deleted_at を立てる。端末は updated_at の続きから取りに行く
- **権限の規則**：チームの内容を読み書きできるのは「メンバーで、かつチームが有効」のとき。有効とは、特別扱いの印があるか、運営者の契約が有効でそのチームに枠が割り当てられていること。チームの作成、枠の割り当て、招待、参加、メンバーの削除は、サーバー側の関数（RPC）を通す
- **課金の確認**：Appleからの契約状態の通知を受けてチームの枠に反映する処理が要る。自前（Supabaseの関数）で作るか、RevenueCatのような課金の仲介サービスを使うかは未決



### 10-6. 進める順番（決定）

iOSで無料版、続けてチームプランまで出し、そのあとAndroid版に進む。

1. 無料版をストアに出す（今の機能、1台で完結、課金なし）。分析は全期間を使えるが、「正式版では有料になる」ことをアプリ内に明記する（あとで有料にしたときの反発を避けるため）。買い切りは入れない
2. アカウント、チーム、招待、試合の送信を作り、チームプランを始める。同時に、分析の無料範囲を直近3試合に絞る
3. Android版を出す（メンバーがiPhoneに限られる状態を解消する。それまではファイルで共有）
4. 要望があれば、1試合を複数人で同時に記録する機能

### 10-6b. 端末側の実装（2026-11-19 着手）

サーバーの土台（10-5b）に、アプリ側をつないだ。**接続先（`EXPO_PUBLIC_SUPABASE_URL`、`EXPO_PUBLIC_SUPABASE_KEY`）を入れていないビルドでは、チームプランの画面は出ず、今までと同じ動きになる。**

できていること

- **置き場所**：端末のチーム（名簿）と試合に `space_id` を持たせた。空なら個人、入っていればそのチーム。一覧・分析・新規試合は、いま開いている置き場所だけを対象にする。ホームの上部で切り替える（進行中の試合があるあいだは切り替えられない）
- **サインイン**：メールアドレスに届く6けたのコードで行う（パスワードなし）。Apple・Google のサインインは次の段階（アプリの作り直しが要るため）
- **チーム**：作る、名前を変える、招待を送る（共有シート）、招待のコード・リンクで入る、メンバーを外す、抜ける、削除する。作ったときに、個人の自チーム名簿をチームの名簿に写す
- **チームに送る**：終了した個人の試合を、チームへ**移す**（写しを残さない。同じ試合が2か所にあると、直した内容が食い違うため）。自チーム側の選手は、チームの名簿と背番号・氏名で突き合わせ、名簿にいなければ足す。同じ背番号に別の名前の選手がいるときは結び付けない。同じ日・同じ対戦の試合がチームにあれば、送る前に知らせる
- **同期**：送ってから受け取る。開いたとき・前面に戻ったとき・未送信があれば20秒ごと・何もなくても2分ごと。ホームに状態を1行で出す
  - 送る：行ごとの印（`dirty`）を見て、変わった行だけをIDで上書き保存する。印はSQLiteのトリガーが付けるので、記録の処理（`repo.ts`）は同期を意識しない
  - 削除：端末で消したチームの行は控え（`sync_tombstones`）に残し、サーバーでは `deleted_at` を立てる
  - 受け取る：テーブルごとに `updated_at` の続きから。未送信の変更がある行は端末の内容を残す（あとから送ったほうが残る）
  - ほかの人が記録した試合を消そうとして断られたら、端末の削除を取り下げて元に戻す（画面でも、本人と運営者以外には削除を出さない）
- **チームの自チーム名簿のID**は `own-<チームID>` に固定する（2台で同時に作っても二重にならない）
- **サインアウト・チームから外れたとき**：そのチームの内容を端末から消す（サーバーには残る）。個人の記録は残る
- **バックアップ**：個人の置き場所だけを書き出す。読み込み先も個人

- **分析の無料範囲**：個人の置き場所では直近3試合だけを集計する（期間の切り替え、選手ごとのページ、全内容のまとめPDFは出さない）。チーム（契約中）は制限なし。`EXPO_PUBLIC_PAYWALL=1` を付けたビルドだけで有効になる。契約の機能ができるまでは付けない
- **アカウントの削除**：設定 → チームプラン → アカウントを削除。運営しているチームは内容ごと消え、ほかのチームからは抜ける。そこで記録した試合はチームに残り、記録した人は空になる（その試合を消せるのは運営者だけ）。個人の記録は端末に残る

まだのこと（次の段階）

- 契約（アプリ内課金）と枠の割り当ての画面。いまは、サーバーで特別扱いの印を付けたチームだけが使える
- Apple・Google でのサインイン
- 招待のリンクを、LINE などで押せる形（https）にする。いまは `benchbook://join/<コード>` で、押せないアプリではコードを貼る
- 契約が切れたチームにある「自分が記録した試合」を、個人へ戻す
- クラウドのSupabaseプロジェクトの作成と、メール送信（確認コード）の設定

### 10-7. 決まっていないこと

- [ ] 無料版に広告を入れるか。入れる場合の場所（ホームのバナー、共有時の全画面広告）。入れると、広告SDKの追加、追跡の許可ダイアログ、プライバシー表示の変更が必要になる。代わりに同じ場所へチームプランの案内を出す案もある
- [ ] Android版をどの段階で作るか（今のコードはAndroidでも動くが、配布・課金・実機確認の作業が要る）
- [ ] メンバーの人数に上限を設けるか
- [ ] 料金（案：1チームあたり月980円、年9,800円＝2か月分引き。チームの会費で払う前提なら月500円との差は効きにくく、採算に必要なチーム数が半分になる。値上げは既存の契約者の同意が要るので、安く始めてあとで上げるより、この額で始めるほうが安全）
- [ ] サーバーの有料プランに切り替える時期（最初は無料枠で始め、契約するチームが出てから切り替える案）
- [ ] 個人だけを有料にするプランを出すか。出す場合、1人だけのチームを作るのと何が違うか（価格、共有なし）
- [ ] 未加入で記録した過去の試合を、チームに入ったあとでまとめて送れるか
- [ ] 解約後、サーバー上のデータを何日残すか
- [ ] 課金の確認を自前で作るか、仲介サービス（RevenueCatなど）を使うか。料金と、段階つき商品・チームへの枠の割り当てに対応できるかを確認する
- [ ] Supabaseの料金プラン（無料枠は一定期間使われないと停止する仕様があるため、公開時は有料プランが前提になる見込み。最新の条件を確認する）
- [ ] 運営者の交代（機種変更、担当の引き継ぎ）と、契約の引き継ぎ

- [ ] 選手の氏名の扱い（運営者が本人以外の氏名を入力し、サーバーに置くことになる点。法律面の確認）
- [ ] ストア公開に必要なもの：プライバシーポリシー、利用規約、問い合わせ先、アカウント削除の機能、スコアシート様式の権利確認、アプリ名の商標確認
